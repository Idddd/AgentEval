# Single-Flow Agent Workbench Design

**Date:** 2026-07-30

**Status:** Approved for implementation planning

**Audience:** Product and engineering

**UI language:** English

## Goal

Replace the current combination of global sidebar navigation, nested Agent
tabs, and session-only demo state with one clear workflow:

`Agent -> Dataset -> Evaluation -> Report`

The selected Agent becomes the stable context for the rest of the workflow.
Users can prepare and edit a Dataset, run an evaluation, and reopen or compare
durable Reports without losing the existing modular Agent and Tool model.

This revision also restores the full Dataset editing experience, removes the
misleading empty `test` Agent from the UI, and makes test results the primary
content of every Report.

## Product Principles

1. **One navigation system.** The sidebar is the only primary navigation. Pages
   do not contain a second row of workflow tabs.
2. **Agent is selected, not created, in the demo workflow.** The Agent page is
   the only place where the active Agent can change. Agent creation and editing
   controls are outside the primary demo flow.
3. **Downstream context is locked.** Dataset, Evaluation, and Report always use
   the selected Agent. Users return to the Agent page to change it.
4. **Lists begin empty and grow through explicit actions.** Dataset cases are
   added manually, imported as JSON, generated by an LLM, or completed from
   existing coverage.
5. **Runs and Reports are durable.** Refreshing the application or returning
   later must preserve run time, results, revisions, evidence, Judge output,
   token use, and cost.
6. **Results come first.** Pass/fail outcomes and failure reasons appear before
   supporting evidence, Judge details, tokens, and cost.
7. **Evidence is informative, not a prerequisite for PASS.** Missing Judge or
   Tool evidence leaves the corresponding Report section empty; it does not by
   itself change a passing test to `FAIL` or `INCOMPLETE`.
8. **The demo proves extensibility.** The seeded Agent remains the main demo
   object, while its modular Agent revision and Tool bindings demonstrate that
   other Agents and Tools can be supported later.

## Selected Approach

Use a single-level Streamlit workbench backed by the existing SQLite domain
repositories.

- The sidebar contains `Agent`, `Dataset`, `Evaluation`, `Report`, and
  `Settings`.
- Session state stores the active page and selected `agent_id` only as UI
  context.
- SQLite remains the source of truth for Agents, Dataset revisions, Eval Runs,
  and Reports.
- An idempotent demo seeder creates a real Permission Compliance Agent, Dataset,
  and baseline Report when the fixture is absent.
- Existing Dataset editing, run persistence, comparison, and Report history
  services are reused instead of maintaining a parallel session-only demo.

This approach was selected over a session-only demo because session state
cannot provide durable report history or revision comparison. It was selected
over a separate demo-history store because two Agent identities would make
navigation and comparison ambiguous.

## Information Architecture

### Sidebar

The sidebar is always visible and contains exactly these workflow destinations:

1. `Agent`
2. `Dataset`
3. `Evaluation`
4. `Report`
5. `Settings`

Each item dispatches a real page. Placeholder destinations are removed. The
active page has a visible selected state, and keyboard activation follows the
same route as mouse activation.

A small `Reset demo` action remains at the bottom for repeated presentations.
Reset clears transient UI state and returns to the Agent page. It does not
delete or recreate Agents, Datasets, Runs, or Reports.

### Agent Context Rules

- The Agent page owns the Agent selector.
- Dataset, Evaluation, and Report show a read-only Agent context header.
- They do not render an Agent selector, Add Agent button, or editable Agent
  fields.
- If the selected Agent no longer exists or no valid Agent is selected, a
  downstream route redirects to Agent with an English instruction to select an
  Agent.
- Selecting a different Agent clears page-local choices such as selected
  Dataset revision, selected run, and selected Report. It does not alter any
  persisted records.
- Persisted placeholder records with `current_revision == 0`, including the
  existing blank `test` record, are hidden from selectors and cards. They are
  not deleted automatically.

## Page Designs

### 1. Agent Home

The Agent page is both the selector and the overview for the selected Agent.
It contains:

1. **Agent selector** — valid persisted Agents only, with the seeded Permission
   Compliance Agent selected by default.
2. **Basic information** — name, description, current Agent revision, adapter,
   model/runtime summary, and last updated time.
3. **Target Tools** — the selected revision's modular Tool bindings, including
   Tool type, availability, permission requirement, and custom test focus.
4. **Latest Report** — timestamp, Dataset revision, Agent revision, pass rate,
   pass/fail counts, and change from the preceding Report.
5. **Quality trend** — pass rate over run time when at least two Reports exist.
6. **Cost trend** — token cost over run time when at least two Reports contain
   cost data.
7. **Report history** — newest first, with time, revisions, status, result,
   pass-rate delta, and cost. Selecting a row opens it on the Report page.

With one Report, the page shows Latest Report and history but no misleading
single-point trend chart. With no Reports, it shows an empty state leading to
Dataset or Evaluation.

### 2. Dataset

The Dataset page restores the existing full case editor and scopes it to the
locked Agent. The initial list may be empty. Users can add cases through:

- manual creation;
- JSON import;
- LLM draft generation;
- LLM coverage completion from existing cases;
- duplication of an existing case.

LLM-generated and imported cases enter a review list first. Users can edit each
case, select the cases to include, and explicitly add them to the Dataset.
Existing cases remain visible after Dataset creation or publication.

The page supports mutable drafts and immutable published revisions. A draft
may be published before Evaluation. The evaluation flow may also publish a
snapshot of the current draft after explicit confirmation, using the existing
Dataset revision service.

If LLM generation is unavailable or returns invalid JSON, the page shows a
specific English error while manual entry and JSON import remain usable.

### 3. Evaluation

The Evaluation page displays a read-only summary of:

- selected Agent and Agent revision;
- selected Dataset and Dataset revision;
- case count;
- evaluator configuration;
- estimated or recorded usage fields when available.

Starting an evaluation creates a new immutable Eval Run. For the seeded demo,
the runner uses the real modular Tool bindings with deterministic local
adapters so that Tool execution evidence is produced without an external
dependency. Every rerun creates a new Run and Report; it never overwrites a
historical result.

The page reports run progress and case-level status. When the Run finishes, the
application selects the new Report and navigates to Report.

Only an actual execution error or a failed test assertion makes a case fail.
Missing optional Judge output or missing Tool evidence does not change the
case's pass/fail result.

### 4. Report

The Report page opens the most recently selected Report, falling back to the
latest Report for the active Agent. Historical Reports can be selected without
changing the active Agent.

Content order reflects user importance:

1. **Test Results** — overall PASS/FAIL summary, pass rate, case table, failed
   assertions, and failure reasons.
2. **Tool Evidence** — requested/executed Tool, arguments, sanitized output,
   timing, and trace identifiers when recorded.
3. **LLM Judge** — scores and reasons when recorded.
4. **Comparison** — current versus prior Report, regressions, resolved failures,
   Agent/Dataset revision differences, and metric deltas.
5. **Usage & Cost** — input/output/total tokens, model, and monetary cost at the
   bottom of the page.

Every empty optional section displays `Not available for this run` or an empty
state. It must not display an error badge, alter pass rate, or turn the Report
into `INCOMPLETE` solely because Judge or Tool evidence is missing.

Comparison is available when the active Agent has at least two compatible
Reports. The default comparison is the selected Report against the immediately
preceding Report, with controls to choose another historical Report.

### 5. Settings

Settings is a real status page rather than a placeholder. It summarizes:

- LLM provider configuration and reachability;
- Langfuse configuration and reachability;
- SQLite database location/status;
- demo fixture version and availability.

Secrets are never displayed. Settings changes that are not part of the current
demo may remain read-only status values.

## Demo Fixture and Persistence

### Idempotent Seed

At application startup, a domain-level `seed_demo_workspace` operation checks
for a stable fixture marker such as `permission-compliance-v1`. It must not use
the weaker condition "any Agent exists."

When the marker is absent, the operation creates:

- Permission Compliance Agent, revision 1;
- three modular Tool bindings demonstrating Agent, HTTP API, and local adapter
  connection types;
- Permission Compliance Regression Dataset with six cases, published as
  revision 1;
- one immutable all-pass baseline Eval Run and Report.

The baseline gives Agent Home an initial historical result. The next primary
demo Run intentionally exposes one permission-bypass regression, producing a
visible change from 100% to approximately 83.3%.

When the marker exists, startup does not duplicate records, overwrite user
edits, or recreate deleted history. Fixture creation uses the same repositories
and immutable revision structures as non-demo data.

### Durable History

Report history is queried by stable `agent_id` and ordered by completion time.
Each Report references immutable Agent and Dataset revisions and snapshots the
case results necessary to render it later.

Refreshing the browser, restarting Streamlit, or pressing Reset demo preserves
history. A new Agent revision can be evaluated against the same or a newer
Dataset revision, and Report comparison calls out both configuration and result
changes.

The old session-only Demo Report is not migrated. The seeded SQLite baseline
and all newly persisted Runs become the official history.

## Result Semantics

Case status is determined from execution and assertions:

- `PASS`: execution completed and all required assertions passed.
- `FAIL`: execution failed or one or more required assertions failed.

Judge output and Tool evidence are nullable supporting data. Their absence is
not an assertion failure unless a particular Dataset case explicitly defines
the presence of that evidence as a required assertion. In the ordinary demo
cases, missing optional evidence leaves Report cells blank or `Not available`
while the result remains `PASS`.

Run and Report aggregate status derives from case execution status and case
results, not optional presentation data. Operational failures that prevent a
case from executing still remain visible and cannot be silently counted as a
pass.

Color supports but does not replace status text. PASS uses a clear green label
and FAIL a clear red label, with accessible contrast in the light theme.

## State and Routing

The shell owns these session values:

- `active_page`;
- `selected_agent_id`;
- page-local selected Dataset, Run, and Report identifiers;
- transient editor/form state.

Sidebar actions update `active_page` through a single routing function. Page
renderers never create their own primary navigation. Direct downstream access
validates `selected_agent_id` before reading page-specific state.

Reset demo clears these session values and form drafts, then selects `Agent`.
It does not call Streamlit cache-clearing APIs and therefore never produces the
framework's Clear caches confirmation dialog.

## Error and Empty States

- **No valid Agent:** show Agent page with selector guidance.
- **Revision-zero placeholder:** hide it; do not delete it.
- **No Dataset cases:** preserve add/import/generate actions above the empty
  list.
- **LLM unavailable:** retain manual and JSON paths.
- **Dataset is a draft:** offer explicit publish/snapshot behavior before run.
- **No Reports:** show an Evaluation call to action.
- **One Report:** show Latest Report and history; hide trends and comparison.
- **Missing Judge or Tool evidence:** show an empty optional section; retain the
  computed PASS/FAIL result.
- **Run execution failure:** show the affected case as FAIL with its error; do
  not fabricate an empty successful Report.

## Testing Strategy

### Unit Tests

- sidebar labels map to real page routes;
- selecting an Agent is permitted only on Agent Home;
- downstream pages validate and lock `selected_agent_id`;
- revision-zero Agents are excluded from visible choices;
- demo seeding is idempotent and fixture-marker based;
- Reset demo clears only session/UI state;
- Report aggregation ignores absent optional Judge/Tool evidence;
- actual execution or assertion failures remain FAIL;
- Report history ordering and previous-Report selection are stable;
- trend data is emitted only for sufficient historical points.

### Integration Tests

- the existing Dataset editor supports manual add, JSON import, LLM review,
  coverage completion, edit, selection, and publication through the new page;
- Evaluation persists a Run, case results, and Report for the locked Agent;
- a second run remains distinct and can be compared with the baseline;
- browser/session restart preserves Agent history;
- Agent revision changes appear in comparison metadata;
- Tool evidence and Judge fields render when present and remain empty when
  absent without changing PASS;
- token and cost values persist and render below results and comparison.

### UI Checks

- each sidebar destination changes the visible page;
- no nested workflow tabs remain;
- Agent controls are absent from downstream pages;
- all user-facing copy is English;
- PASS and FAIL remain legible without relying only on color;
- Dataset add actions remain visible above an empty or populated case list;
- Report visual priority is Results, Evidence, Judge, Comparison, then Usage &
  Cost;
- Reset returns to Agent without clearing persisted history or showing the
  Streamlit Clear caches dialog.

The complete existing automated suite must also remain green.

## Out of Scope for This Demo Iteration

- production-grade Agent creation and deletion workflows;
- full editing of Agent and Tool configuration from the UI;
- multi-user authorization and tenancy;
- deletion or migration of malformed historical Agent records;
- remote production deployment and secrets management;
- automatic migration of old session-only demo results.

## Acceptance Criteria

The design is complete when a user can select the Permission Compliance Agent
on Agent Home, inspect its history, add or generate Dataset cases, run an
evaluation without changing Agent context, inspect result-first Reports, and
compare the new Report with the durable baseline. Refreshing or resetting the
demo must preserve the Report history. Missing Judge or Tool evidence must
leave those Report fields empty without changing an otherwise passing result.
